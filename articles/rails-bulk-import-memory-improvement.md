こんにちは！アルダグラムでエンジニアをしている kageyama です

> 私たちが開発している「KANNA」のバックエンド（Ruby on Rails）で、案件インポートの上限を引き上げるための取り組み記録です。
> 単純な上限値の変更ではなく、**Worker のメモリ枯渇** という壁にどう向き合い、計測 → クイックウィン → 根本対応と段階的に削っていったか、コードを交えて紹介します。

## TL;DR

- 既存案件インポートの処理は **行数 × カスタマイズ項目数** に比例してメモリを食う。500 件で数百MB、仮に単純計算で 3,000 件なら **1.5GB 超**。Worker が落ちると他ジョブまで影響される。
- `get_process_mem` で**フェーズ別にメモリを計測**してボトルネックを可視化。
- 「早期 nil 化 + GCクリア 、 関連キャッシュの `reset`」という**クイックウィン**を行なった。
- 結果として、Excelシート **3,000 行 x 70列のインポート処理を 800MB 程度** に抑えられた。
- **全会社で数千~数万件に対応する**ための根本対応（行単位トランザクション化など）は「今後の TODO」として残っている。

---

KANNA では「案件」が中心的なドメインモデルです。顧客・物件・担当者・カスタマイズ項目・工程・写真など、ほぼすべての機能が案件にぶら下がります。

そのため、他システムからの乗り換えや大量データの初期投入で使われる **Excel からの案件インポート** は、導入のしやすさを左右する重要な機能です。ですが、現状の上限は **500 件**であり、数万件規模の案件を抱える顧客からは「もっと一度に入れたい」という声が継続的に上がっていました。

ただ上限を引き上げると **Worker のメモリが枯渇** します。厄介なのは、メモリ不足が案件インポート単体に閉じないこと。例えば案件保存に連動して動く、案件に紐づく会社への同期バッチが、メモリ不足で Worker 再起動を繰り返す、といった周辺ジョブへの波及も観測されました。特定処理を別workerで作動させることで回避ができますが、一方で根本治療とはなりません。

### 規模感のリアル

「カスタマイズ項目」は会社ごとに自由に定義でき、ここがパフォーマンスに影響します。極端な会社では以下のような規模でした。

| 指標                                 | 値               |
| ------------------------------------ | ---------------- |
| 1 案件あたりの最大カスタマイズ項目数 | 約 **100 項目**  |
| 案件数が最も多い会社                 | 約 **6〜7 万件** |

インポート 1 行は「案件本体 + 顧客 + 物件 + 担当者 + カスタマイズ項目 N 個」。**N が数十〜数百になり得る**ため、行数だけでなく列数（項目数）方向にもメモリが膨らみます。

## まず計測する：フェーズ別メモリプロファイリング

推測ではなく計測から始めます。`get_process_mem` gem をローカルに入れ、インポートの処理を**フェーズ境界ごと**に記録しました。

500 件インポート時の内訳（消費メモリ 数百MB）：

| フェーズ               | メモリ増分 | 内容                            |
| ---------------------- | ---------- | ------------------------------- |
| `Excelパース処理`      | 約 40MB    | RubyXL で Workbook を丸ごと展開 |
| `AR経由でのデータ生成` | 約 53MB    | 全行分の AR オブジェクトを構築  |
| `DB保存`               | 約 65MB    | 全件 save! + 関連保存           |
| `依存処理`             | 約 19MB    | 依存関係・サマリー再集計        |
| `後処理`               | 約 18MB    | 監査ログ・通知の発火            |

ここから見えた構造的な問題は

1. **全行を一度に ActiveRecord オブジェクトとしてメモリに載せ、単一の巨大トランザクションで保存している**。ピークメモリが処理の最後まで高止まりする。
2. **カスタマイズ項目が、ネストした関連レコードの自動保存（ネスト属性）経由で各案件にぶら下がる**。`列数 × 行数` のオブジェクトが `@models` 全体で同時に生存する。
3. ActiveRecord の `after_save` で **案件ごとに監査ログ・通知ジョブを発火**。3,000 件なら 3,000 回。

500 件で 数百MB なら、単純比例で 3,000 件は **1.5GB 超**。通常時に本番 Worker のメモリが枯渇することはありませんが、大量インポート処理が走ると危険です。

## ステップ 1：クイックウィン 〜「使い終わったら、すぐ手放す」〜

大改修をするのは、デグレのリスクが高いうえに工数も大きくかかります。ミニマムで効果的な策として、まずは **挙動を変えずにメモリのピークと滞在時間を下げる**「クイックウィン」から着手しました。狙いは一貫して **「参照を切って GC の対象にする」** ことです。

### 1-1. 使い終わった大きな中間データを早期に nil 化する

インスタンス変数で取り回している巨大な中間 AR データは、使い終わったタイミングで明示的に `nil` を代入して参照を切り、GC の対象にします。

具体的には、顧客・物件を保存するために `uuid → レコード` や `行番号 → レコード` のマッピングを抱えた巨大ハッシュ（`@clients_by_id` / `@clients_by_row` / `@properties_by_id` / `@properties_by_row` など）は、各保存ループの中でしか使いません。ループを抜ければ後続フェーズでは一切参照されないにもかかわらず、インスタンス変数のままだとインポート処理オブジェクトが生きている限りメモリに居座り続けます。そこで、保存ループが終わった直後にこれらへ `nil` を代入し、参照を切って GC が回収できる状態にします。

### 1-2. `@models`（AR オブジェクト群）を「軽量ハッシュ」に置き換える

1-1 は「後続で一切使わないデータをそのまま捨てる」話でしたが、こちらは少し事情が違います。全行分の案件を保持する `@models` は、保存後の `after_save` でも参照され続けていました。とはいえ必要なのは「`uuid → id` のマッピング」や「更新案件の id 一覧」といった**ごく一部の情報**だけでした。巨大な ActiveRecord オブジェクトの配列そのものを握り続ける必要はありません。

つまり「一部だけ使うから丸ごと残す」のではなく、**必要な情報だけを軽量な構造に抽出してから、本体（`@models`）を手放す**という置き換えを行います。これが 1-1 の単純な nil 化との違いです。

```ruby
# after_save で必要な情報だけを軽量な構造に抽出してから @models を解放する
@saved_model_uuids = @models.map(&:uuid)

# 大量の AR オブジェクトはもう不要 → 参照を切って GC 対象に
@models = nil
GC.start
```

> **`GC.start` の明示呼び出しについて**
> Ruby/Rails で `GC.start` を手で呼ぶのは、一般には**非推奨**とされています。Ruby の GC は十分に賢く、いつ回収するかはランタイムに任せるのが基本です。手動で割り込むとかえって不要なフル GC を誘発し、CPU 時間を浪費しかねません。
> しかし今回のように、**「もう使わないと確実に分かっている巨大オブジェクトを手放した直後」** という状況では、回収を GC の判断任せにせず明示的に促す価値があると考えています。`@models = nil` で参照を切っても、実際に解放され再利用可能になるのは次に GC が走ったタイミングです。そこを待たずに `GC.start` で前倒しすることで、後続フェーズが積み上げるメモリとの**ピークの重なり**を避けられます。メモリ逼迫を抑えること自体が目的のこの処理では、CPU コストを払ってでも先に回収しておくメリットが上回る、という判断です。
> ただしあくまで**例外的な最終手段**であり、乱発は禁物です。原則は「使い終わった参照を都度切る」「`find_each` / `in_batches` で逐次化する」で構造的にピークを下げ、それでも残る山にだけ `GC.start` を当てます。

### 1-3. ネスト保存で積み上がるカスタマイズ項目を `reset` する

これが「カスタマイズ項目の多い会社」に一番効きました。

ActiveRecord は、親レコードにぶら下がる**子レコードをロードしたりビルドしたりすると、それを親オブジェクトの「関連キャッシュ」として保持し続けます**。便利な仕組みですが、親 1 件あたりの子が多く、かつ親が大量にある状況では、このキャッシュが積み重なって無視できないメモリを占めます。今回は 1 案件あたりのカスタマイズ項目（子レコード）が数十〜数百あり、それが全案件分まとめて生き続けていました。

ポイントは、**保存さえ済めばこの関連キャッシュはもう要らない**ということです。そこで保存直後に関連を `reset` してキャッシュを破棄し、参照を切ります。

```ruby
model.save!
model.custom_field_values.reset
```

> `association.reset` は ActiveRecord の関連キャッシュを破棄するメソッドです。「ロード済みの関連オブジェクトをもう使わない」と分かっているループでは、地味ですが効果的なメモリ解放手段になります。

## 今後の TODO：根本対応で「全社数千件」へ

クイックウィンでピークは大きく下がりましたが、それでも**カスタマイズ項目が約 70 項目あると 3,000 行で 800MB 程度**を消費します。これは「全行を一度に load して単一トランザクションで保存する」という**構造**が残っているためで、行数・項目数を増やすほどメモリは膨らみます。

**全会社で安心して数千件に対応する**には、以下の根本対応が必要だと考えており、今後の TODO として整理しています。これらが実現できれば、上限引き上げが可能になります。

### TODO 1. 行単位トランザクション化

クイックウィンの限界は、**「全行を一度に load して単一トランザクションで保存する」構造そのもの**にあります。これを **「1 件保存したら、その都度コミットして参照を手放す」** 逐次処理へ切り替えれば、ピークメモリは件数に対して頭打ちになります。あわせて、1 行ごとに成否を判定できるので**部分成功**（「2,500 件成功・500 件失敗」）を表現でき、エラーも行単位で記録できます。

ただし「全件まとめて」から「1 件ずつ」への移行は、見た目以上に設計の作り替えを伴います。たとえば**レコード間に依存関係がある**場合（親子の階層構造など）は保存順序を保証する必要があり、**全体を見て初めて成立するチェック**（合計件数の上限など）は事前計算に寄せる必要があります。また、二値（成功/失敗）だった結果が三値（一部成功）に増えることは、API を消費するフロント/アプリにとって**互換性を壊す変更**になり得るため、リリース順序の調整も必要です。「逐次化」はメモリには効きますが、こうした周辺設計まで含めて初めて成立する、というのが見立てです。

### TODO 2. 監査ログと通知の「集約」

案件保存に連動して**1 件ごとに発火している監査ログ・通知**は、3,000 件なら 3,000 回のジョブとメモリを生みます。ここは **「件数ぶん発火」から「まとめて 1 回」へ集約**するのが筋です。監査ログはインポート完了時に 1 件へまとめ、通知も「複数の案件に追加されました」のようにユーザー単位で束ねる、という方針です。

集約のために処理の最後まで持ち回る状態も、AR オブジェクトではなく **ID や識別子といった軽量な値**に限定し、本当に必要になった時点で DB から読み戻す——という、ここまでと同じ「重いものを抱え続けない」原則を貫きます。

## 結果

クイックウィン（ステップ 1）を積み上げた結果、実データ（案件約 6 万件・カスタマイズ約 70 項目の顧客）での計測は次のように改善しました。

|                                    | 行数 / 項目数         | メモリ消費  |
| ---------------------------------- | --------------------- | ----------- |
| **Before（クイックウィン適用前）** | 3,000 行 / 約 70 項目 | **1.5GB超** |
| **After（クイックウィン適用後）**  | 3,000 行 / 約 70 項目 | **約800MB** |

ピークが 1.5GB → 800MB 程度まで下がり、`Worker` のメモリ枠（本番 8GB）に対して現実的な水準になりました。

全会社で数千件に対応するには、前述の「今後の TODO」（行単位トランザクション化など）による根本対応が必要だと考えています。

## まとめ：メモリ最適化の型

1. **推測せず計測する** — `get_process_mem` でフェーズ別に可視化。どこを削れば効くかは測らないと分からない。
2. **使い終わったら即手放す** — 早期 nil 化、関連の `reset`、軽量ハッシュへの置き換え。「参照を切る」のが GC への一番の近道。
3. **“全件一括” を疑う** — 単一の巨大トランザクション・全件 load・per-record のジョブ発火は、件数が増えると線形以上に効いてくる。逐次処理 + 集約に作り直す（＝今回の「今後の TODO」）。
4. **影響範囲を広く見る** — 今回のような大きいJobの場合、同じ Worker の周辺ジョブ、監査ログ・通知の発行数など、様々な影響を考慮して設計する。

「案件」という中核ドメインだからこそ、インポートの体験はプロダクトの導入障壁に直結します。まずはクイックウィンでメモリのピークを大きく削り、一定水準まで上限を引き上げられるところまで来ました。残る根本対応をやり切って、すべての顧客の「数千件を一度に入れたい」に応えていきたいですね。
